# 工作原理

## 设计目标

项目只解决一个问题：在不修改 Codex 客户端的前提下，给实时语音输入增加本地、默认关闭的唤醒门控。

设计优先级：

1. 失败时静音。
2. 未唤醒音频不进入 Codex。
3. 不修改 Windows 默认音频设备。
4. 不保存音频或全文转写。
5. 设备选择必须明确，禁止错误回退到系统扬声器。

## 组件

### `VoiceGate`

两状态状态机：

- `closed`：音频替换为同形状的零值数据。
- `open`：复制并放行音频。
- `fail_safe()`：任何异常强制回到 `closed`。

只有完整匹配“小欧”和“结束”才改变状态，控制词本身不作为普通文本转发。

### `SherpaKeywordRecognizer`

使用 sherpa-onnx 开放词表关键词检测，在本地识别两个控制词。它不进行通用全文听写。

### `AudioDelayGate`

为音频增加短时延迟，让关键词识别结果能在对应控制词到达输出之前改变门控状态。这样可以抑制控制词本身进入虚拟麦克风。

### `LocalAudioRouter`

把关键词事件、门控状态和延迟音频组合起来。识别异常会触发失败关闭。

### `preflight_virtual_cable`

从 Windows 音频设备中查找唯一、兼容的 VB-CABLE 播放端：

- 名称必须是 `CABLE Input`。
- 必须具备输出通道。
- 必须通过目标采样率检查。
- 重复、缺失或格式不兼容均拒绝启动。
- 不回退到系统默认扬声器。

### `run_virtual_cable_bridge`

同时打开：

- 真实麦克风：单声道、16 位、16 kHz。
- VB-CABLE 播放端：单声道、16 位、目标端原生采样率。

门控后的 PCM 从 16 kHz 重采样到 VB-CABLE 当前原生采样率（已验证环境为 48 kHz），再写入虚拟线。程序退出时关闭两个音频流。

## 音频数据流

```text
真实麦克风
  ├─> 本地关键词识别 ─> 状态事件
  └─> 延迟缓冲 ───────> 门控 ─> 重采样 ─> CABLE Input
                                                  │
                                                  ▼
                                        CABLE Output 虚拟麦克风
                                                  │
                                                  ▼
                                             Codex 客户端
```

## 为什么要用虚拟音频设备

Codex 客户端没有提供可供此项目调用的“只转发某些音频帧”接口。VB-CABLE 提供一个 Windows 播放端和一个录音端：本项目写入 `CABLE Input`，Codex 从 `CABLE Output` 读取。

VB-CABLE 是独立第三方驱动，不属于项目源代码，也不会被仓库打包。

## 失败保护

以下情况会拒绝启动或立即关闭：

- 找不到真实麦克风。
- 输入设备被识别为虚拟音频线。
- 找不到唯一可用的 `CABLE Input`。
- 目标格式不受支持。
- 音频回调报告错误。
- 音频队列溢出。
- 虚拟输出欠载。
- 关键词识别器抛出异常。

“程序已经静音”不等于“Windows 或 Codex 已经恢复设置”。操作者仍需退出实时语音并把 Codex 麦克风恢复为“系统默认”。

## 非目标

- 不自动启动或关闭 Codex 实时语音。
- 不更改 Windows 麦克风权限。
- 不为不同 Codex 任务保存不同输入设备。
- 不隐藏正在使用麦克风的事实。
- 不承诺零误唤醒、零漏唤醒或适合安全关键场景。
- 不替代 Codex/OpenAI 的隐私设置和数据政策。
